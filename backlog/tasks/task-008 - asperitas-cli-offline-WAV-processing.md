## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
A CLI that runs any `Processor` over a WAV file. This is the substrate golden-file regression tests are built on, and the cheapest way to hear a change without a flash cycle.

```
asperitas process in.wav out.wav --param damping=0.3 --param structure=0.7
```

Use `hound` for WAV I/O. Handle sample-rate mismatch by calling `set_sample_rate` with the file's actual rate rather than resampling or refusing — the trait was designed for exactly this.

Parameter parsing is the first consumer of the knob-to-parameter mapping policy that will later be shared with the Pod and the TUI. Keep that mapping somewhere both can reach; don't bury it in CLI argument handling.

Set up the test corpus directory (`audio/`) at the same time:
- **synthetic signals** generated by the CLI itself — impulses, sweeps, plucked-string stubs. Deterministic and diffable.
- **real instrument recordings** committed to git, per the corpus decision: short (2–5 s), mono, 48 kHz, to keep the repo manageable.

Golden-file regression: freeze known-good output for a given input + parameter set, assert future output matches within float tolerance. **Goldens are regenerated only by an explicit command, never automatically** — a golden diff in a review means 'listen to this before accepting it', not 'run the update command'. That distinction is the entire value of the mechanism.

Analysis output (impulse/frequency response, RMS, spectrogram) is a later ticket; leave room for it in the command structure but don't build it now.
